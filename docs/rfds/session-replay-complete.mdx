Author(s): [nikita-ashihmin](https://github.com/nikita-ashihmin)

## Elevator pitch

> What are you proposing to change?

Add a `replay_complete` session update. The Agent sends it once, after the last replayed history notification of a session load and before the response.

- A Client learns that it holds the full history as soon as the replay ends, not when the Agent finishes the rest of its setup.
- A Client can tell a complete replay from a truncated one when the load fails, is cancelled, or the connection drops.
- The signal applies to v1 `session/load` and to v2 `session/resume` with a `replayFrom` cursor.
- In v1, the Agent advertises the signal with a capability and sends it only to Clients that opt in. In v2, it is required whenever history is replayed.

The response keeps its current meaning. It still tells the Client that the session is ready for prompts.

## Status quo

> How do things work today and what problems does this cause? Why would we change things?

In v1, [`session/load`](/protocol/v1/session-setup#loading-sessions) replays the conversation as `session/update` notifications. "When **all** the conversation entries have been streamed", the Agent responds. In v2, [`session/resume`](/protocol/v2/draft/session-setup#resuming-sessions) with `replayFrom: { "type": "start" }` has the same contract: the Agent replays all retained history before it responds.

The response is the only signal that the replay is over. But the response also means "the session is ready", and Agents often do expensive work after the replay and before the response. Measurements from one Client (JetBrains) against current adapters:

- **claude-agent-acp** replays the transcript in parallel with the start of the Claude CLI. The history was complete after 0.04–0.9 s. The response came at 0.75–1.9 s on an idle Windows machine. On a first cold start it came 4.3–4.7 s after the history was complete. On a loaded macOS machine where several agents started at once, it came 8–9 s after the history.
- **codex-acp** waits up to 1 s for a network account read before the replay starts (about 0.7 s on an idle machine). The history itself then took 55 ms.

These numbers describe one implementation on specific machines. They are not protocol facts. They show that the gap between "history complete" and "response" can be seconds, and that it depends on work the Client cannot see.

During that gap the Client holds a complete history that it cannot show with confidence. It has two options:

1. **Wait for the response.** The user looks at an empty or spinning session for seconds while the full transcript is already in memory.
2. **Guess with a quiet-period debounce.** The Client renders once no update arrives for some time. This is wrong for paged producers: codex-acp reads history in pages of 100 items with one RPC per page, so a pause between pages looks like the end. A wrong guess makes the Client render the transcript in several pieces. Each piece re-lays out the transcript and can build lazily rendered content near the viewport again.

There is a second problem. When a load fails after part of the replay, for example because the Agent crashed, the Client cannot tell whether it received the whole history. This matters for Clients that persist the replay or rebuild a local transcript from it. Such a Client must not replace a good local copy with a truncated one.

### Prior art

JetBrains uses a private `_meta` contract between its cloud agent and its IDE Client:

- Every replayed notification carries `_meta.loadSessionReplayIndex`, a 0-based position.
- Optionally, it also carries `_meta.loadSessionReplaySize`. Despite the name, the value is the **last index**, not the count. This naming trap is a lesson for any standard field.
- The last replayed notification carries `_meta.loadSessionEndOfRecordedHistory: true`.

The Client renders the history when it sees the end flag. If a load ends with marked notifications but without the end flag, the Client treats the replay as truncated and does not rebuild a transcript from it. claude-agent-acp and codex-acp are adding the same marks.

The idea works, but every pair of implementations that wants it must agree on private keys. This RFD proposes to standardize the idea. It does not propose to standardize these key names.

## What we propose to do about it

> What are you proposing to improve the situation?

### The `replay_complete` update

When the Agent has sent every history entry it selected for a replay, it sends one `session/update` with the `replay_complete` variant:

```json
{
  "jsonrpc": "2.0",
  "method": "session/update",
  "params": {
    "sessionId": "sess_789xyz",
    "update": {
      "sessionUpdate": "replay_complete"
    }
  }
}
```

The variant has no required fields. It accepts `_meta` like every other update.

The rules:

- The Agent **MUST** send `replay_complete` exactly once for each request that replays history. It **MUST** send it before the response to that request.
- The Agent **MUST** send it for an empty history too. Then it is the first `session/update` for that request.
- The Agent **MUST NOT** send it for a request that does not replay history: v1 `session/resume`, v2 `session/resume` without `replayFrom`, and `session/new`.
- The Agent **MUST NOT** send it as a guess. If it cannot finish the replay, it does not send it.

The Client **MAY** render the replayed history as soon as it receives `replay_complete`. The response still means that the session is ready. The Client **SHOULD** keep prompt input and session controls disabled until the response arrives.

### No live updates before the marker

The Client can trust the marker only if everything before it is history. So, from the moment the Agent receives a replaying request until it sends `replay_complete`, every `session/update` it sends for that session **MUST** be replayed history.

Live events that happen in this window wait until after the marker. Examples are the chunks of a turn that is still in flight, launch progress notices, `available_commands_update`, `config_option_update`, and v2 `state_update`. The Agent buffers them and sends them after `replay_complete`. One JSON-RPC connection delivers messages in order, so the buffering is local to the Agent.

A turn that is in flight during a load is split at a cut point. The retained part up to the cut is history and comes before the marker. The rest is live and comes after it. In v2, message updates and chunks are keyed by `messageId`, so the live chunks append to the replayed message.

This rule covers `session/update` only. It does not change when the Agent can send requests such as `session/request_permission`. Those **SHOULD** also wait until after the marker, because a Client may not show them before it shows the history.

### Truncated and failed replays

With the signal negotiated, the Client can classify every outcome:

| What the Client received                       | Meaning                                                                                                                                  |
| ---------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| `replay_complete`, then a success response     | Complete history. Session ready.                                                                                                         |
| `replay_complete`, then an error response      | Complete history. The session failed to start. The Client can show the history read-only.                                                |
| No `replay_complete`, then an error response   | Truncated replay. The Client **MUST NOT** treat the received updates as the full history, for example to replace a persisted transcript. |
| No `replay_complete`, then cancellation or EOF | Truncated replay, as above.                                                                                                              |
| No `replay_complete`, then a success response  | Protocol violation. The success response still certifies the history, as in today's contract. The Client **MAY** log the violation.      |

`replay_complete` says that the Agent sent everything it **selected** for this replay. It does not say that the Agent retained everything that ever happened. Agents may already drop live-only messages or old history. Agents **SHOULD** report known gaps with an advisory mechanism such as [session notices](/rfds/session-notices), sent after the marker.

### Capabilities

**v1.** The v1 `SessionUpdate` union is closed. An older Client can fail to parse an unknown variant. So the signal needs both sides to opt in.

The Agent advertises support:

```json
{
  "agentCapabilities": {
    "loadSession": true,
    "sessionCapabilities": {
      "replayComplete": {}
    }
  }
}
```

The Client advertises support:

```json
{
  "clientCapabilities": {
    "session": {
      "replayComplete": {}
    }
  }
}
```

Omission or `null` means unsupported. `{}` means supported. The Agent sends `replay_complete` only when the Client advertised it. The Client expects `replay_complete`, and applies the truncation rules above, only when the Agent advertised it.

**v2.** The v2 `SessionUpdate` union is open under the [enum variant extension rule](/rfds/v2/enum-variant-extension), so an older v2 Client ignores the variant. The signal is cheap for the Agent. We propose that it is **required** in v2: every replaying `session/resume` ends its replay with `replay_complete`. No capability is needed.

### Subagent sessions

A load of a parent session can also replay child sessions, as described in the [Subagent Sessions RFD](/rfds/subagents#reconnection-and-replay). There is one marker for each request. The Agent sends it on the parent `sessionId`, after all history it selected for the parent and the children. Children do not get their own marker.

The marker does not move the freshness boundary of that RFD. Child work state and mutation capabilities that arrive before the response stay historical. They do not authorize Client-initiated mutations.

### v2 replay cursors

`replay_complete` means "all entries selected by the `replayFrom` cursor have been sent". For `{ "type": "start" }`, that is all retained history. Future cursors use the same rule without change. If a future cursor selects no entries, the marker is the first update, as for an empty history.

## Shiny future

> How will things will play out once this feature exists?

A Client opens a saved session. The history appears as one complete transcript as soon as the Agent has streamed it. A "Starting agent..." indicator then covers the remaining setup until the response arrives and prompt input opens. There is no debounce timer and no transcript that builds up in several pieces.

When the Agent crashes during a load, the Client knows that the replay was cut short. It keeps its persisted copy and shows an error, and it does not replace the copy with a truncated transcript.

Adapters stop inventing private `_meta` keys for this. A Client implements one rule that works with every Agent that advertises the capability.

## Implementation details and plan

> Tell me more about your implementation. What is your detailed implementation plan?

1. **Schema (v1, unstable).** Add a `ReplayComplete` variant with only `_meta` to `SessionUpdate`. Add `replayComplete` to the Agent `SessionCapabilities` and to the Client `ClientSessionCapabilities`. Keep both behind an unstable feature flag.
2. **Schema (v2).** Add the `replay_complete` variant to the v2 `SessionUpdate` union.
3. **Docs.** Update [Session Setup](/protocol/v1/session-setup) for v1 and the v2 draft. The sequence diagram gets a `replay_complete` step between "All content streamed" and the response. Document the ordering rule and the truncation table.
4. **SDKs.** Expose the variant and the capabilities in the Rust and TypeScript SDKs. A helper in the Agent SDKs can buffer live updates for a session while its replay runs.
5. **Adapters and Clients.** Implement in claude-agent-acp and codex-acp, and in the JetBrains Client. The existing `_meta` marks can stay for a transition period. The last marked notification is followed by `replay_complete`.

## Frequently asked questions

> What questions have arisen over the course of authoring this document or during subsequent discussions?

### What alternative approaches did you consider, and why did you settle on this one?

We evaluated three designs.

**(a) A dedicated `session/update` variant sent once after the replay.** This RFD proposes it.

- It works for an empty history without a special case.
- The Agent does not need to know which entry is last while it sends it. A paged producer sends the marker after its last page returns. No lookahead buffer is needed.
- It adds one small notification per load, and nothing to each replayed update.
- It cannot separate interleaved live updates from history on its own. The ordering rule above fixes this. The Agent already controls the order of its writes, so the rule is cheap.
- In v1 it needs a Client capability because the union is closed.

**(b) Replay metadata on each replayed notification.** Each replayed update carries a position, and the last one carries an end flag. This is the JetBrains prior art.

- It lets the Client tell replayed updates from live ones even when they interleave. This is its main benefit.
- To set the end flag, the Agent must know which notification is last. A streaming or paged producer must hold back one notification until it knows whether more follow. This adds latency equal to one page fetch for codex-acp.
- An empty history has no notification to carry the end flag. It needs a second mechanism, which in practice is design (a).
- Positions add bytes to every replayed update and add little value. One JSON-RPC connection is ordered and does not drop messages. A count also invites errors, as `loadSessionReplaySize` shows: the name says "size" but the value is the last index.
- Old Clients ignore unknown fields, so no Client capability is needed. This is its second benefit.

The ordering rule in design (a) gives the benefit of (b) without its costs. Implementations can still send per-notification positions in `_meta` if they need them.

**(c) A capability-gated two-step flow where the response comes first and the history streams after it.**

- It changes what the response means. Today a success response certifies the history. Under (c) it would not, so the Client still needs an end marker for the stream after the response. This is design (a) with a reordered response.
- The [Subagent Sessions RFD](/rfds/subagents#reconnection-and-replay) uses the response as the freshness boundary for child state and controls. History after the response breaks that boundary.
- A Client could send a prompt while history still streams. The new turn and old history would then interleave in one stream.
- Its one benefit is that the Client gets `configOptions` and modes earlier. But the expensive Agent work happens before the response in either case. So (c) does not make the session usable sooner. It only moves the wait.

We did not choose (c).

### Why a `session/update` variant and not a new notification method?

SDKs dispatch all `session/update` notifications through one handler in order. A separate method such as `session/replay_complete` can reach the application on a different path and lose its order relative to the last replayed update. Unknown notification methods are also handled differently across v1 implementations.

### Why not let the Agent respond earlier instead?

The v1 contract ties the response to the end of the replay, and Clients rely on that. Some Agent work, such as starting a CLI or a network account read, really must finish before the session can take prompts. The fix is to report the two milestones separately, not to merge them earlier.

### What does the Client do with updates after `replay_complete` but before the response?

They are live. The Client applies them like any live update. In v2, they include current snapshots such as `state_update`. The subagent freshness rules still apply to them until the response arrives.

### Can a Client load the same session twice at the same time on one connection?

The marker carries the `sessionId`, not the request ID. With two concurrent replaying requests for one session, the Client cannot tell which marker belongs to which request. Clients **SHOULD NOT** send a second replaying request for a session while the first one is pending. See the open questions.

### Does the marker cover `session/fork`?

No. This RFD covers requests that replay history today. Any future method that replays history should adopt the same marker.

### Open questions

- **Name.** `replay_complete` is short. `history_replayed` and `replay_end` are alternatives.
- **v2: required or capability?** This RFD proposes required. A capability would let simple v2 Agents skip it, but then every v2 Client needs the debounce fallback again.
- **Request correlation.** Should the marker carry an optional field that identifies the request, to support concurrent loads of one session?
- **A resume position.** Should the marker carry an opaque cursor that a future `replayFrom` variant accepts, so a Client can later replay only newer history?
- **Known gaps.** Should the marker carry an optional flag that says the Agent knows its retained history is incomplete? Or is a session notice enough?
