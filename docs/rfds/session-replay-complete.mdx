Author(s): [nikita-ashihmin](https://github.com/nikita-ashihmin)

## Elevator pitch

> What are you proposing to change?

Add a `replay_complete` session update. The Agent sends it once, after the last replayed history entry of a session load and before the response.

With it, a Client can:

- show the full history as soon as the replay ends, not when the Agent finishes its setup;
- tell a complete replay from a truncated one when the load fails, is cancelled, or the connection drops.

The signal applies to v1 `session/load` and to v2 `session/resume` with a `replayFrom` cursor. The response keeps its meaning: the session is ready for prompts.

## Status quo

> How do things work today and what problems does this cause? Why would we change things?

In v1, [`session/load`](/protocol/v1/session-setup#loading-sessions) replays the conversation as `session/update` notifications, and the Agent responds after all entries. In v2, [`session/resume`](/protocol/v2/draft/session-setup#resuming-sessions) with `replayFrom: { "type": "start" }` has the same contract.

The response is the only signal that the replay is over. The response also means "the session is ready", and an Agent can do slow work after the replay and before the response. For example, claude-agent-acp replays the transcript while the Claude CLI starts. We measured the response 0.7–1.9 s after the end of the replay on an idle machine, and 4–9 s on a cold start or a loaded machine.

This causes two problems:

1. **The Client cannot show the history early.** It holds the full history but does not know that it is full. It must wait for the response, or guess with a quiet-period timer. A timer is wrong for a paged producer, because a pause between pages looks like the end. A wrong guess renders the transcript in several pieces.
2. **The Client cannot detect a truncated replay.** When a load fails after part of the replay, the Client does not know whether it got the whole history. A Client that persists the replay must not replace a good local copy with a truncated one.

## What we propose to do about it

> What are you proposing to improve the situation?

### The `replay_complete` update

After the Agent sends every history entry it selected for a replay, it sends one `session/update` with the `replay_complete` variant:

```json
{
  "jsonrpc": "2.0",
  "method": "session/update",
  "params": {
    "sessionId": "sess_789xyz",
    "update": {
      "sessionUpdate": "replay_complete"
    }
  }
}
```

The variant has no required fields. It accepts `_meta` like every other update.

Rules:

- The Agent **MUST** send `replay_complete` exactly once for each request that replays history, before the response to that request.
- The Agent **MUST** send it for an empty history too. Then it is the first `session/update` of that request.
- The Agent **MUST NOT** send it for a request that does not replay history: v1 `session/resume`, v2 `session/resume` without `replayFrom`, and `session/new`.
- The Agent **MUST NOT** send it when it cannot finish the replay.

The Client **MAY** render the history when it receives `replay_complete`. The Client **SHOULD** keep prompt input disabled until the response.

### No live updates before the marker

Every `session/update` that the Agent sends for the session between the request and `replay_complete` **MUST** be replayed history.

The Agent buffers live events in this window and sends them after the marker. Examples are the chunks of a turn in flight, launch progress, `available_commands_update`, `config_option_update`, and v2 `state_update`. One JSON-RPC connection is ordered, so the buffer is local to the Agent.

A turn in flight during a load is split at a cut point. The part up to the cut is history and comes before the marker. The rest is live and comes after it. In v2, chunks are keyed by `messageId`, so the live chunks append to the replayed message.

Agent requests such as `session/request_permission` **SHOULD** also wait until after the marker, because a Client may not show them before the history.

### Outcomes

| What the Client received                       | Meaning                                                                                          |
| ---------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| `replay_complete`, then a success response     | Complete history. Session ready.                                                                 |
| `replay_complete`, then an error response      | Complete history. The session failed to start. The Client can show the history read-only.        |
| No `replay_complete`, then an error response   | Truncated replay. The Client **MUST NOT** use the updates as the full history.                   |
| No `replay_complete`, then cancellation or EOF | Truncated replay, as above.                                                                      |
| No `replay_complete`, then a success response  | Protocol violation. The success response still certifies the history. The Client **MAY** log it. |

`replay_complete` means that the Agent sent everything it **selected** for this replay. It does not mean that the Agent retained all history. Agents **SHOULD** report known gaps with a mechanism such as [session notices](/rfds/session-notices), after the marker.

### Capabilities

**v1.** The v1 `SessionUpdate` union is closed, and an older Client can fail on an unknown variant. So both sides opt in.

The Agent advertises support:

```json
{
  "agentCapabilities": {
    "loadSession": true,
    "sessionCapabilities": {
      "replayComplete": {}
    }
  }
}
```

The Client advertises support:

```json
{
  "clientCapabilities": {
    "session": {
      "replayComplete": {}
    }
  }
}
```

Omission or `null` means unsupported, and `{}` means supported. The Agent sends `replay_complete` only to a Client that advertised it. The Client applies the outcome table only when the Agent advertised it.

**v2.** The v2 `SessionUpdate` union is open under the [enum variant extension rule](/rfds/v2/enum-variant-extension), so an older v2 Client ignores the variant. We propose that the marker is **required** in v2 for every replaying `session/resume`. No capability is needed.

### Subagent sessions

A load of a parent session can also replay child sessions, see the [Subagent Sessions RFD](/rfds/subagents#reconnection-and-replay). There is one marker for each request. The Agent sends it on the parent `sessionId`, after the history of the parent and the children.

The marker does not move the freshness boundary of that RFD. Child state that arrives before the response stays historical.

### v2 replay cursors

`replay_complete` means that all entries selected by the `replayFrom` cursor were sent. For `{ "type": "start" }`, that is all retained history. If a cursor selects no entries, the marker is the first update.

## Shiny future

> How will things will play out once this feature exists?

A Client opens a saved session and shows the full transcript as soon as the Agent streams it. A "Starting agent..." indicator covers the rest of the setup until the response opens prompt input. The Client needs no timer, and the transcript does not build up in pieces.

When the Agent crashes during a load, the Client knows that the replay was cut short. It keeps its persisted copy and shows an error.

## Implementation details and plan

> Tell me more about your implementation. What is your detailed implementation plan?

1. **Schema (v1, unstable).** Add a `ReplayComplete` variant with only `_meta` to `SessionUpdate`. Add `replayComplete` to the Agent `SessionCapabilities` and to the Client `ClientSessionCapabilities`, behind an unstable feature flag.
2. **Schema (v2).** Add the `replay_complete` variant to the v2 `SessionUpdate` union.
3. **Docs.** Update [Session Setup](/protocol/v1/session-setup) for v1 and the v2 draft. Add a `replay_complete` step to the sequence diagram between "All content streamed" and the response. Document the ordering rule and the outcome table.
4. **SDKs.** Expose the variant and the capabilities in the SDKs. An Agent SDK helper can buffer live updates while a replay runs. A Client SDK must deliver the updates of a loading session before the response. For `session/load` and `session/resume`, the Client knows the session ID before the request, so the SDK can register the session handler first. [kotlin-sdk#146](https://github.com/agentclientprotocol/kotlin-sdk/pull/146) does this for the Kotlin SDK.
5. **Adapters.** Implement in claude-agent-acp, see [#1361](https://github.com/agentclientprotocol/claude-agent-acp/pull/1361), and in other adapters that do work between the replay and the response.

## Frequently asked questions

> What questions have arisen over the course of authoring this document or during subsequent discussions?

### What alternative approaches did you consider, and why did you settle on this one?

**(a) One update after the replay.** This RFD proposes it.

- It works for an empty history.
- The Agent does not need to know which entry is last. A paged producer sends the marker after its last page.
- It adds one small notification per load.
- It cannot separate live updates from history alone. The ordering rule fixes this.
- In v1 it needs a Client capability, because the union is closed.

**(b) Replay metadata on each replayed notification:** a position on each, and an end flag on the last.

- It separates replayed updates from live ones when they interleave.
- To set the end flag, the Agent must hold back one notification until it knows that no more follow. For a paged producer this adds one page fetch.
- An empty history has no notification for the flag, so it needs design (a) too.
- Positions add bytes to every update, and one JSON-RPC connection is ordered already.

The ordering rule of (a) gives the benefit of (b) without its costs.

**(c) The response first, then the history.**

- A success response no longer certifies the history, so the Client still needs an end marker. This is (a) with a reordered response.
- It breaks the freshness boundary of the [Subagent Sessions RFD](/rfds/subagents#reconnection-and-replay).
- A prompt could interleave with the history in one stream.
- The slow Agent work still comes before the session is usable.

### Why a `session/update` variant and not a new notification method?

SDKs dispatch all `session/update` notifications through one ordered handler. A separate method can reach the application on another path and lose its order relative to the last replayed update.

### Why not let the Agent respond earlier?

Clients rely on the response as the end of the replay. Some Agent work, such as a CLI start, must finish before the session can take prompts. The two milestones need two signals.

### What does the Client do with updates after `replay_complete` but before the response?

They are live, and the Client applies them as live updates. The subagent freshness rules apply until the response.

### Can a Client load the same session twice at the same time on one connection?

The marker carries the `sessionId`, not the request ID, so the Client cannot match two markers to two requests. Clients **SHOULD NOT** send a second replaying request for a session while the first one is pending.

### Does the marker cover `session/fork`?

No. A future method that replays history should use the same marker.

### Open questions

- **Name.** Alternatives are `history_replayed` and `replay_end`.
- **v2: required or capability?** This RFD proposes required. With a capability, every v2 Client needs the timer fallback again.
- **Request correlation.** Should the marker carry an optional request identifier?
- **Resume position.** Should the marker carry an opaque cursor for a future `replayFrom` variant?
- **Known gaps.** Should the marker carry a flag for incomplete retained history, or is a session notice enough?
