Author(s): [anna239](https://github.com/anna239)

## Elevator pitch

> What are you proposing to change?

Introduce a new `plan_update` session update type that supports multiple plan formats (item-based, and markdown text with an optional path to the plan file), multiple concurrent plans via IDs, and plan removal. The existing `plan` session update type remains unchanged for backward compatibility.

## Status quo

> How do things work today and what problems does this cause? Why would we change things?

- The `plan` session update contains `entries: Vec<PlanEntry>` — a flat list of items with priority/status
- Plans are one-way notifications (agent → client) via `session/update`
- No plan identity — each update replaces the previous plan entirely
- No way to remove/dismiss a plan once sent
- Only one plan representation (structured items) — no support for free-form markdown plans or for plans the Agent keeps in a file

## What we propose to do about it

> What are you proposing to improve the situation?

Add a new `SessionUpdate` variant — `plan_update` — that carries a `plan` field. The `plan` field is a tagged union (discriminated by `type`) with the following variants:

| Type       | Description                                                           | Specific fields                    |
| ---------- | --------------------------------------------------------------------- | ---------------------------------- |
| `items`    | Structured entries (same semantics as today's `plan`)                 | `entries: PlanEntry[]`             |
| `markdown` | Agent provides raw markdown text, and optionally the path of its file | `content: string`, `path?: string` |

All variants carry a required `planId: string` that identifies the plan, and an optional `_meta` for extensibility.

Additionally, introduce a `plan_removed` session update type that carries only a `planId` to signal dismissal. This keeps `plan_update` focused purely on content updates and makes removal a distinct, self-describing event.

The existing `plan` session update type is **not modified** and continues to work as before. Agents that want multi-plan support, new plan formats, or removal capabilities use `plan_update` and `plan_removed` only when the client advertises `plan`; otherwise they fall back to the existing `plan` session update type.

### Client capabilities

Add to `ClientCapabilities`:

```
plan?: PlanCapabilities
```

This field is optional. When present as `{}`, it signals the client supports the `plan_update` and `plan_removed` session update types. When omitted, the client does not advertise support, and the agent must fall back to the existing `plan` session update type.

When the Client advertised `plan`, Agents **SHOULD** send their plans with `plan_update` instead of `plan`.

### Multiple plans

The `planId` field on every plan variant identifies a specific plan.

- Each `plan_update` replaces the whole plan with that `planId`, whatever its `type`, including when the type differs from the previous update.
- Clients track plans by ID. Different plans may use different types (for example, one `items` plan and one `markdown` plan).
- For `items` plans, the Agent sends the complete list of entries in each update. An empty `entries` array empties the plan. Clients **MAY** hide an empty plan.

### Markdown plans

`content` is required and holds the whole plan as markdown.

`path` is optional. An Agent that keeps the plan in a file sets `path` to that file. `path` **MUST** be an absolute path. Omitting `path` and sending `null` both mean the plan has no file.

`content` is the plan to display whether or not `path` is set. Clients render `content` and don't need to read the file. A Client that can reach the file can use `path` to open it.

`content` is a snapshot. When the plan changes, the Agent sends another `plan_update`, as it does for a plan without a file.

### Plan removal

The Agent sends a `plan_removed` session update with the plan's `planId` to remove it. This is a separate session update type from `plan_update`, so content updates and lifecycle events stay distinct.

- Agents **SHOULD** send `plan_removed` when a plan is cancelled, for example when the user rejects it or the Agent abandons it. A finished plan doesn't need to be removed.
- Clients **MUST** ignore `plan_removed` for a `planId` they don't know.

### Protocol versions

In ACP v1, `plan_update` and `plan_removed` require the Client's `plan` capability, as described above. The v1 `PlanUpdateContent` has no fallback for unknown `type` values, so a v1 Client that receives an unknown plan type fails to parse the notification. A new v1 plan type would need its own capability.

In ACP v2, the [v2 Plan Variants RFD](/rfds/v2/plan-variants) makes `plan_update` with `type: "items"` the only plan update and removes the `plan` capability. `markdown` and `plan_removed` remain unstable in v2 and need no capability. v2 Clients that don't know a plan type treat it as replacing the plan with that `planId` through the unknown plan-content fallback.

## Shiny future

> How will things play out once this feature exists?

Agents will be able to present plans in the format most natural to them — structured checklists for step-by-step execution, or markdown for free-form design docs, with the path of the plan file when the Agent keeps one. Clients that support `plan_update` can show multiple concurrent plans (e.g., a high-level strategy and a detailed implementation checklist), and dismiss plans that are no longer relevant. Clients that don't advertise `plan` continue to receive the existing `plan` updates with no changes.

## Implementation details and plan

> Tell me more about your implementation. What is your detailed implementation plan?

### Protocol implementation

The schema is implemented behind the `unstable_plan_operations` Cargo feature:

- ACP v1 defines `PlanUpdate`, `PlanUpdateContent`, `PlanItems`, `PlanMarkdown`, `PlanRemoved`, `PlanId`, and `PlanCapabilities`, and adds `plan` to `ClientCapabilities`.
- ACP v2 defines `markdown` and `plan_removed` on top of the stable `items` plan update.
- The draft protocol guides describe both versions. See the [v1 guide](/protocol/v1/draft/agent-plan#plan-operations) and [v2 guide](/protocol/v2/draft/agent-plan#unstable-plan-operations).

The feature remains behind `unstable_plan_operations` and is not included in the stable schemas.

### Json format examples

Existing `plan` (unchanged):

```json
{
  "sessionUpdate": "plan",
  "entries": [{ "content": "Step 1", "priority": "high", "status": "pending" }]
}
```

Item-based (`plan_update`):

```json
{
  "sessionUpdate": "plan_update",
  "plan": {
    "type": "items",
    "planId": "plan-1",
    "entries": [
      { "content": "Step 1", "priority": "high", "status": "pending" }
    ]
  }
}
```

Markdown:

```json
{
  "sessionUpdate": "plan_update",
  "plan": {
    "type": "markdown",
    "planId": "plan-1",
    "content": "## Steps\n- [ ] Refactor module\n- [ ] Add tests"
  }
}
```

Markdown with the path of the plan file:

```json
{
  "sessionUpdate": "plan_update",
  "plan": {
    "type": "markdown",
    "planId": "design-doc",
    "content": "## Steps\n- [ ] Refactor module\n- [ ] Add tests",
    "path": "/home/user/project/PLAN.md"
  }
}
```

Removal:

```json
{
  "sessionUpdate": "plan_removed",
  "planId": "plan-1"
}
```

## Frequently asked questions

> What questions have arisen over the course of authoring this document or during subsequent discussions?

### Why a new session update type instead of extending the existing `plan`?

The existing `plan` variant flattens `Plan`'s `entries` field directly into the `SessionUpdate` discriminated union object. Adding a nested `plan` field, optional `planId`, and polymorphic types to the same variant would require breaking the existing format or complex dual-deserialization logic. A new `plan_update` variant avoids this, but agents must only send it to clients that advertised `plan`; clients that do not advertise support can continue to receive the existing `plan` update.

### Why a separate `plan_removed` session update type instead of a removal variant inside `plan_update`?

Keeping removal as a separate session update type means `plan_update`'s `type` discriminator only covers content variants (`items`, `markdown`), making the schema cleaner.

### Why is the plan file a `path` on `markdown` plans and not its own plan type?

An earlier revision had a `file` plan type that carried only a `uri`. A Client had to read the file to show the plan's content, and a Client that doesn't share a filesystem with the Agent couldn't show it at all. Neither Agent adapter listed above sent `file` plans. The Claude Agent adapter left them out because a `file://` URI only resolves on the Agent's machine.

With `path` on the `markdown` plan, the Agent always sends the content, so every Client that renders markdown plans can show the plan. The path is extra information for Clients that can reach the file.

`path` is an absolute path and not a URI, like the paths in tool call locations and diffs.

### Why plan-specific markdown and not a generic markdown content API?

A generic "agent shares markdown document" API would be simpler and more reusable. However, keeping it plan-typed enables clients to build plan-aware UX: selecting plan steps for partial execution, tracking plan progress, showing plan history. A generic markdown block wouldn't carry this semantic meaning. If future use cases need generic markdown sharing, that can be a separate feature.

### When should an Agent remove a plan?

When the plan is cancelled, for example when the user rejects it or the Agent abandons it. A finished plan still shows what the Agent did, so the Agent doesn't need to remove it. Clients can hide or collapse finished plans themselves.

### What alternative approaches did you consider, and why did you settle on this one?

1. **Extending the existing `plan` variant**: Would break backward compatibility or require complex dual-format deserialization.
2. **`"type": "removed"` variant inside `plan_update`**: Instead of a separate `plan_removed` session update type, removal could be a variant in the `plan_update` tagged union (e.g., `"type": "removed"`). This keeps the entire plan lifecycle within a single update type. The tradeoff is that the `type` discriminator mixes content variants with a lifecycle event, making the schema less clean.
