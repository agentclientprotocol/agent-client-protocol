## Elevator pitch

> What are you proposing to change?

Add a `failure` session update: a history entry that records why foreground work did not produce what was asked, such as an error, a token limit, or a refusal. Unlike the idle `state_update`, a `failure` has an ID, keeps its position in the conversation, and is replayed on `session/resume`. Clients can show a failed turn after a reload and offer Retry only for the latest failure.

## Status quo

> How do things work today and what problems does this cause? Why would we change things?

The [prompt lifecycle RFD](./prompt.mdx#report-failures-after-insertion) reports how foreground work ended in the idle `state_update`, with a stop reason and, for errors, an `error`. This works for a live Client, but `state_update` is a snapshot of the current state, not a history entry:

- Replay does not include past states. Resume sends only the current state after replay.
- The next `running` state replaces the snapshot, so only the latest stop reason is known, and only until new work starts.
- The snapshot has no position in the conversation. A Client cannot place the failure after the message it belongs to.
- The snapshot has no ID. A Client that gets the same failure twice, for example live and then after a resume, cannot tell that both are one failure.

As a result, a failed turn disappears when the user reloads the session. The user sees their message without an answer and without an explanation. The same happens when work stops at a token or turn limit, or when a refusal cuts an answer short: the partial answer looks complete. Notices do not help: by design they are not replayed and must not report errors that end work.

Agent runtimes already keep this information. The Codex app-server stores each turn with its `status` and `error` in the thread history. Claude Code stores API errors as entries in the session transcript. ACP has no update that can replay them, so adapters drop them or invent their own `_meta` entries.

## What we propose to do about it

> What are you proposing to improve the situation?

Add a `failure` session update:

```json
{
  "jsonrpc": "2.0",
  "method": "session/update",
  "params": {
    "sessionId": "sess_abc123",
    "update": {
      "sessionUpdate": "failure",
      "failureId": "fail_7f3a",
      "stopReason": "error",
      "error": {
        "code": -32603,
        "message": "Rate limit reached. Try again in 15 seconds.",
        "data": { "kind": "rate_limited", "retryable": true }
      }
    }
  }
}
```

- `failureId` is required and is generated by the Agent. It is unique within the session.
- `stopReason` and its fields use the same stop reason union as the idle `state_update`. `error` exists only on `stopReason: "error"` and uses the JSON-RPC error object, including the classification fields from the [Error Classification RFD](/rfds/error-classification).
- `failure` is an upsert keyed by `failureId`. A second update with the same ID replaces the entry. It does not add a new one.

The standard stop reasons that are failures are `error`, `max_tokens`, `max_turn_requests`, and `refusal`. Work that ends with `end_turn` finished, and its answer is already in history. Work that ends with `cancelled` was stopped by the user or Client on purpose. An RFD that adds a stop reason says whether it is a failure. Until then, it is not.

### Agent rules

- Agents **SHOULD** send a `failure` when foreground work ends with `error`, `max_tokens`, `max_turn_requests`, or `refusal`.
- Agents **MAY** send a `failure` with a custom stop reason when it means that the work failed.
- Agents **MUST NOT** send a `failure` for `end_turn` or `cancelled`, or without a stop reason.
- The `failure` comes after all other updates for the work that ended and before the idle `state_update` that ends it.
- The idle `state_update` still carries the stop reason and `error`. It alone ends foreground work. A `failure` does not change the session state.
- Retention follows the same rules as messages. The Agent is not required to retain failures. If it retains one, it **MUST** replay it at the same position in history and **SHOULD** keep the same `failureId`.

### Client semantics

- A `failure` with a known `failureId` is the same failure. It replaces the earlier entry and does not add a new one.
- The idle `state_update` that follows a `failure` reports the end of the same work. It is not a second failure.
- A failure is current while it is the latest entry in the conversation and the session is idle. A later user message or failure makes it history.
- Clients **MUST** accept unknown stop reasons in a `failure`.

### Replay example

After `session/resume` with `replayFrom: { "type": "start" }`, the Agent replays the failed turn in order:

```jsonc
{ "sessionUpdate": "user_message", "messageId": "msg_1", "content": [ ... ] }
{ "sessionUpdate": "agent_message", "messageId": "msg_2", "content": [ ... ] }
{ "sessionUpdate": "failure", "failureId": "fail_7f3a", "stopReason": "error", "error": { ... } }
{ "sessionUpdate": "state_update", "state": "idle", "stopReason": "error", "error": { ... } }
```

The last `state_update` is the current-state snapshot that resume always sends. If later work succeeded, the snapshot shows that state, and the `failure` stays in history.

## Shiny future

> How will things will play out once this feature exists?

A user reloads a session and still sees why the last turn failed, with the same message and recovery hint as before the reload. Older failures stay in place in the conversation. A Retry button appears only for the failure that is still current, and old buttons stop working on their own, without extra tokens or revision checks.

## Implementation details and plan

> Tell me more about your implementation. What is your detailed implementation plan?

1. Add the `failure` session update to the v2 schema, reusing the stop reason union of the idle `state_update`.
2. Update the Claude and Codex adapters to send failures live. Replay can come later: the Codex app-server already keeps `status` and `error` on each turn, while Claude Code transcripts need the error fields that the SDK's session history does not expose today.
3. Document the ordering rule and the client semantics in the v2 prompt lifecycle guide.

### Compatibility

`failure` is a new session update type. Older v2 Clients ignore unknown update types and keep using the idle `state_update`. No capability is needed, because the idle `state_update` still reports everything that live Clients need. This RFD does not change v1.

## Frequently asked questions

> What questions have arisen over the course of authoring this document or during subsequent discussions?

### The prompt lifecycle RFD rejected a separate error update before idle. Why is this different?

That RFD rejected an `error` update followed by `idle` because the two signals would have to agree, and the protocol would need rules for an error without an idle. Here the roles do not overlap. The idle `state_update` is still the only signal that work ended, and it still carries the stop reason and `error`. The `failure` is history: it adds an ID and a position, and live Clients can ignore it without losing anything. A `failure` without a following idle update ends nothing.

### Why are `end_turn` and `cancelled` not failures?

They are the two outcomes that someone wanted. `end_turn` means the work finished, and its answer is in history. `cancelled` means the user or Client stopped the work on purpose, so there is nothing to explain or recover. The other standard stop reasons mean the work did not produce what was asked. A refusal can also cut an answer short, which looks like a complete answer after a reload.

### Why list the failure stop reasons instead of excluding `end_turn` and `cancelled`?

`stopReason` is an open enum, and not every future stop reason will be a failure. For example, the Anthropic API has a `pause_turn` stop reason for a normal pause after which work continues. A rule like "everything except `end_turn` and `cancelled`" would make such a reason a failure by default, and every new normal outcome would need an exception here. With a list, a new stop reason is not a failure unless its RFD says so. Custom stop reasons have no shared meaning, so Agents decide for themselves.

### Why the name `failure`?

The entry exists only when work did not produce what was asked, and "failure" says that for errors, limits, and refusals alike. It matches how Clients present these entries: as a failure row with a reason and an optional recovery action. It contains no "turn", which v2 avoids in favor of "foreground work".

Other names we considered:

- **`interruption`** - Fits all stop reasons, but in many runtimes "interrupt" means a user cancellation, which this entry excludes.
- **`stop`** - Matches `stopReason`, but reads as a command and suggests an entry for every stop, including `end_turn`.
- **`halt`** or **`termination`** - Neutral, but they describe that work stopped, not that it failed, and "termination" suggests a killed process.
- **`turn_error`** - Clear for errors, but wrong for `max_tokens` and `refusal`, and uses "turn".
- **`turn_outcome`** - Raises the question of why `end_turn` has no entry.
- **`incomplete`** - Used by the OpenAI Responses API for limits, but it is an adjective, and there errors use a separate `failed` status.
- **`system_message`** - Reuses the message rules, but is too broad and invites other content into the same type.

### Why not replay past `state_update` notifications?

States are snapshots. Replaying old states would make Clients switch between `running` and `idle` during replay, and the prompt lifecycle RFD defines resume to send only the current state. A history entry keeps the snapshot simple.

### Why not report the failure as an agent message?

Text in an agent message is not machine-readable. A Client cannot tell a failure from a normal answer, cannot read the error code, and cannot offer recovery. Work can also fail before the Agent sends any message.

### Why is there no resolved state or revision?

The position in history already tells the Client whether a failure is current. A later user message or a later failure makes it history. Revisions and resolution tokens would add rules without new information.

### Should a `failure` reference the user message or a turn ID?

Not in this proposal. ACP v2 has no turn entity, and foreground work does not always start from a prompt. The position after the related messages is enough to show the entry and to find the message to retry.

### What about failures while no work is running?

They are out of scope. A `failure` reports how foreground work ended, so it is not sent while the session is idle. Telling a Client ahead of time that a session cannot continue is a question of session availability, and it needs a separate proposal.

### What alternative approaches did you consider, and why did you settle on this one?

**A replayed notice** - Notices are optional, not replayed, and must not report errors that end work.

**`_meta` on the last agent message** - There may be no agent message, and `_meta` is not interoperable.

**A turn entity like the Codex app-server** - It would solve more, but it is a much larger change to v2. A `failure` entry solves the history problem with one new update type.
