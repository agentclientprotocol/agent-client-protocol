## Elevator pitch

> What are you proposing to change?

This RFD extends the completed [Session List RFD](/rfds/session-list) so that `session/list` can drive a "recent sessions" view without the Client reading agent files from disk. It only adds optional parameters, optional `SessionInfo` fields and one notification on top of the existing method; nothing in the original contract changes for Clients and Agents that do not opt in.

- **`limit`** on the request and a **defined order** (most recently active first), so a Client can ask for "the last 50 sessions of this project" in one round trip.
- **Optional row fields** that such a view shows: the session's **activity state** (`running`, `idle`, `requires_action`, `reviewing`, `error`), when the user last **prompted** it and when its **last turn ended**, the **model** it ran with, the session it was **forked from**, and its **cost** when the Agent already knows it.
- A **list subscription** (`session/list/subscribe`, `session/list/changes`, `session/list/unsubscribe`) on a `cwd`: the Agent pushes the full current row of every session that is created or changes, and the id of every session that is deleted.

Archiving ([#2161](https://github.com/agentclientprotocol/agent-client-protocol/pull/2161)), client-set titles ([#1987](https://github.com/agentclientprotocol/agent-client-protocol/pull/1987)) and liveness probes ([#986](https://github.com/agentclientprotocol/agent-client-protocol/pull/986)) are covered by other RFDs and are out of scope here. This RFD composes with them: the `archived` request parameter and row field from #2161 combine with `limit`, the ordering and `includeWorktrees` defined here (this RFD proposes a three-value `archived` filter, and that archiving a session stops it, see below), and a list subscription is how other Clients learn about archive and rename changes.

## Status quo

> How do things work today and what problems does this cause? Why would we change things?

[`session/list`](/protocol/v1/session-list), as specified by the [Session List RFD](/rfds/session-list), takes `cwd` and `cursor` and returns `sessionId`, `cwd`, `title` and `updatedAt`. Page size and order are left to the Agent; the `limit` and sort parameters were removed from that RFD before it was completed, and its discussion left richer row metadata to later extensions.

IDE clients that show a per-project session history therefore cannot rely on ACP for it, and read each agent's files from disk instead (`~/.claude/projects/*.jsonl`, Codex rollouts, a private `codex app-server`, ...). That means per-agent parsers, file watchers and cost scanners in every client, and they break whenever an agent changes its storage.

Measured against today's adapters on a developer machine:

- **No `limit`, no order.** One adapter returns pages of 1000 rows sorted by file mtime and re-reads every skipped row on later pages (page 5 of 5,000 sessions took 3.5 s). Another returns pages of 25 rows sorted by **creation** time and filters by `cwd` after paging, so the first page for a project is often empty but has a `nextCursor`. A client that wants "the latest 50" has to walk every page.
- **No state.** A list row cannot say that a session is running or waiting for the user. Clients that want a "needs attention" badge parse transcripts themselves.
- **No cost, model or fork origin.** History views show them and many agents know them, but they are either missing or only reachable through `usage_update`/`session_info_update` for sessions that are open on the current connection.
- **No change signal.** `session_info_update` only reaches connections that have the session loaded. A history view does not know that a session was created, renamed or finished by another process, and either polls the whole list or goes stale.

## What we propose to do about it

> What are you proposing to improve the situation?

### Capability

Agents advertise the new behavior with optional markers. Omission or `null` means unsupported, `{}` means supported:

- `limit`: the Agent honors `limit` and `includeWorktrees` on `session/list` and guarantees the order below.
- `subscribe`: the Agent supports `session/list/subscribe`, `session/list/changes` and `session/list/unsubscribe`.

In v1 they extend the existing `SessionListCapabilities`:

```json
{
  "agentCapabilities": {
    "sessionCapabilities": {
      "list": { "limit": {}, "subscribe": {} }
    }
  }
}
```

In v2, `session/list` is part of the baseline session surface, so the markers go into a new optional `list` object under `capabilities.session`:

```json
{
  "capabilities": {
    "session": {
      "list": { "limit": {}, "subscribe": {} }
    }
  }
}
```

The new row fields need no capability: they are optional and Clients ignore what is missing.

### `session/list` request and order

```json
{
  "jsonrpc": "2.0",
  "id": 7,
  "method": "session/list",
  "params": {
    "cwd": "/home/user/project",
    "limit": 50
  }
}
```

- `limit` (optional, integer ≥ 1; omitted or `null` means the Agent's default): the maximum number of sessions in this page. The Agent MAY return fewer and MAY clamp large values; it MUST NOT return more.
- `includeWorktrees` (optional, boolean; omitted or `null` means `false`): also return sessions whose `cwd` is the directory corresponding to `cwd` in each linked Git worktree of the repository, that is, the same path relative to the worktree root. For a repository root this is each worktree root; for `/repo/packages/a` it is `<worktree>/packages/a`. Only existing directories are included, so removed worktrees are not. Without it, `cwd` keeps its current exact-match meaning. Each row reports its own real `cwd`.
- Any other type for `limit` or `includeWorktrees` is an invalid request (`-32602`).
- `archived` (optional; omitted or `null` means `"unarchived"`): which sessions to return. `"unarchived"` returns sessions that are not archived, `"archived"` returns only archived sessions, and `"all"` returns both in one order. Any other value is an invalid request (`-32602`). This widens the boolean `archived` of #2161 (where `true` means both): an archive view needs only the archived sessions, and with the boolean it has to page through every session and filter them out itself.
- Filtering (`cwd`, `includeWorktrees` and `archived`) and the order below apply before pagination. A cursor is valid only with the same `cwd`, `includeWorktrees` and `archived` values that produced it; otherwise the Agent returns `-32602`. `limit` MAY change between pages.
- When `limit` is supported, sessions are ordered by last user activity, descending: `lastPromptAt`, or `updatedAt` for rows without it. Ties are broken by an agent-defined stable key. This is the order history views already use (the user's most recent conversations first), and it does not change when an Agent writes metadata or keeps working on its own. Agents advertising `limit` SHOULD send `lastPromptAt` or `updatedAt` on every row; rows with neither sort last. `updatedAt` keeps its meaning of last activity of any kind.
- A page that carries a `nextCursor` MUST NOT be empty.
- Sub-agent and side-chain sessions are not listed.

### Row fields

New optional fields on `SessionInfo`:

```json
{
  "sessionId": "sess_abc123",
  "cwd": "/home/user/project",
  "title": "Fix the OAuth timeout",
  "updatedAt": "2026-10-06T10:00:00Z",
  "lastPromptAt": "2026-10-06T09:57:40Z",
  "model": "gpt-5.5",
  "forkedFrom": "sess_parent42",
  "state": "requires_action",
  "lastTurnEndedAt": "2026-10-06T09:58:10Z",
  "cost": { "amount": 1.23, "currency": "USD" }
}
```

| Field             | Meaning                                                                                                                                                                                                                                                                                                                                       |
| ----------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `lastPromptAt`    | When the user last sent a prompt. It is the primary sort key of the list; unlike `updatedAt` it does not move when the Agent works on its own.                                                                                                                                                                                                |
| `model`           | The model of the most recent turn, as the Agent names it.                                                                                                                                                                                                                                                                                     |
| `forkedFrom`      | The `sessionId` this session was forked from, when the Agent knows it.                                                                                                                                                                                                                                                                        |
| `state`           | `running`, `idle`, `requires_action` (the v2 `state_update` values) `reviewing` (the agent is in a code-review mode) or `error`: not running, and the last turn ended with an error rather than a user cancel. A new turn clears it. Omitted when the Agent does not know, for example for a session driven by another process it cannot see. |
| `lastTurnEndedAt` | When the last turn ended. Clients use it to decide whether there is unseen output; `updatedAt` cannot be used for that, because it also moves when the user types a prompt elsewhere.                                                                                                                                                         |
| `cost`            | The existing `Cost` type from `usage_update`. Only sent when the Agent already has the value; Agents are not expected to compute it.                                                                                                                                                                                                          |

All values are best-effort snapshots. A field that is missing from a refreshed row means "unknown now": in particular a missing `state` clears a previously reported one. A Client that has the session open keeps using the session's own `session/update` stream, which is authoritative.

### List subscription

A Client that keeps a list on screen subscribes to its `cwd` and receives the new state of every session that changes.

```json
{
  "jsonrpc": "2.0",
  "id": 9,
  "method": "session/list/subscribe",
  "params": { "cwd": "/home/user/project" }
}
```

- `cwd` is required and absolute; anything else is an invalid request (`-32602`). The result is `{ "subscriptionId": "..." }`.
- The subscription covers the sessions of `cwd` and of the same subdirectory in every existing linked Git worktree of its repository, in any archive state. The Client reads the list itself with `session/list` and its own parameters, after subscribing, and applies messages in the order they arrive.

```json
{
  "jsonrpc": "2.0",
  "method": "session/list/changes",
  "params": {
    "subscriptionId": "s1",
    "sessions": [{ "sessionId": "sess_abc123", "...": "..." }],
    "removed": ["sess_old"]
  }
}
```

- `sessions` carries the full current row, as `session/list` returns it, of every covered session that was created or whose title, `lastPromptAt`, `state`, `lastTurnEndedAt`, `cost`, `model`, `forkedFrom` or `archived` changed. A change of `updatedAt` alone is not sent; it arrives with the next change of the row.
- `removed` carries the ids of deleted sessions. Archiving is a row change (`archived` flips); the Client filters by archive state.
- Agents coalesce: at most one change per session per second, and the changes of one moment in one notification.
- Delivery is best effort: an Agent can miss a change, for example a file event or a change made while a backend restarted. While a list is on screen, the Client re-reads it with `session/list` every 30–60 seconds and after reconnecting.
- `session/list/unsubscribe { subscriptionId }` ends a subscription and returns `{}`. A subscription also ends with the connection; there is no expiry. Each subscription is independent, also two on the same `cwd`. Agents MAY cap the number of subscriptions per connection and reject more with `-32602`.

### Archiving stops a session

This RFD proposes one change to the archive semantics of #2161: archiving a session stops it.

- `session/archive` of a session that is open ends any running turn and closes the session, as `session/close` does, before it archives the session. The Agent then sends `session_info_update` with `archived: true`.
- The session stays closed: a later prompt fails as for any closed session. A Client that wants to keep working in it unarchives it and loads it again. `session/unarchive` does not load the session.
- Archiving a session that is not open is unchanged.

Rationale:

- Codex's `thread/archive` already unloads the thread, so an Agent backed by it cannot archive a session and keep it running.
- An archived session that keeps running and changing is confusing in every Client's list: it is hidden from the default view while its state, title and cost keep moving.
- The list subscription then reports a stable archived row: once a session is archived, its row changes only when it is unarchived, renamed or deleted.

## Shiny future

> How will things will play out once this feature exists?

An IDE opens a project and calls `session/list { cwd, limit: 50, includeWorktrees: true }` per agent. The response arrives in a few milliseconds, already sorted, and each row tells the user which sessions are running, which are waiting for them and how much they cost. When the user starts a session in a terminal, finishes one in another window or a turn ends somewhere else, the Agent pushes the changed row to the IDE's subscription and the IDE updates that one row. Clients stop shipping per-agent file parsers and watchers.

## Implementation details and plan

> Tell me more about your implementation. What is your detailed implementation plan?

Prior art: the same design is implemented as a JetBrains `_meta` extension (`_meta.jetbrains.air` capability `sessionIndex`), so it can be tried without protocol changes:

- `claude-agent-acp` ([agentclientprotocol/claude-agent-acp#1268](https://github.com/agentclientprotocol/claude-agent-acp/pull/1268)) keeps an in-memory index over the transcript files. On a real history of 233 sessions, the last 50 sessions of a project take about 80 ms on a cold process and 1.3–4 ms afterwards, against 140–240 ms for today's `session/list`. `state` comes from the SDK for sessions of the process and from Claude Code's live-session registry for others.
- `codex-acp` ([agentclientprotocol/codex-acp#590](https://github.com/agentclientprotocol/codex-acp/pull/590)) passes `cwd`, `limit` and `sortKey: "recency_at"` to `thread/list`. The last 50 sessions of a project take 2–4 ms warm, against an empty first page today. `state` is only reported for threads loaded in the same process.

Both implementations can include sessions from the project's linked Git worktrees, the way the native clients do (Claude Code's `includeWorktrees`, Codex TUI's resume picker), behind the same opt-in `includeWorktrees` flag, and report each row's real `cwd`. Their archive and unarchive follow #2161 (boolean `archived` row field), with the three-value `archived` filter described above, and archiving stops a session that is open, as proposed above.

Plan:

1. Land this RFD as a draft and collect feedback, especially on the capability spelling and on the subscription.
2. Add the fields and the notification to the schema behind the `unstable` feature, and to the v2 draft.
3. Move the two adapters from the `_meta` extension to the protocol fields.

## Frequently asked questions

> What questions have arisen over the course of authoring this document or during subsequent discussions?

### Why bring `limit` back after it was removed from the session list RFD?

Without it, "the latest N sessions" requires walking every page, and agents had to pick page sizes blindly (1000 rows in one adapter, 25 in another). A client-provided upper bound plus a defined order makes the first page useful on its own. Agents can still clamp it.

### Why a subscription with full rows?

Session state changes several times per turn. A rowless "list changed" hint would make every change cost the Client a full page read and a diff, and make the Agent rebuild the page it has just inspected. A subscription sends the one changed row. Rows are full state, so a repeated row cannot corrupt the Client's list, and there are no sequence numbers or resynchronization: a missed change is corrected by the Client's next periodic read.

### Why is `state` optional instead of always present?

An Agent often cannot see sessions driven by another process. For example, a `codex app-server` only knows the status of threads it loaded itself, and none of the native Codex clients show the status of other processes' threads either. The unstable v2 schema has an `unknown` state for open sessions, but in a list most rows would carry it, so the field is omitted instead: absence means "unknown" and keeps the three listed values meaningful.

### How does this relate to `session/status` ([#986](https://github.com/agentclientprotocol/agent-client-protocol/pull/986))?

`session/status` asks one Agent instance whether it is handling one session. `state` describes what a session is doing (running, idle, waiting for the user) for every row of a list. They answer different questions and can coexist.

### How does this relate to session archiving ([#2161](https://github.com/agentclientprotocol/agent-client-protocol/pull/2161)) and client-set titles ([#1987](https://github.com/agentclientprotocol/agent-client-protocol/pull/1987))?

They are complementary. The JetBrains extension also implements archive/unarchive and rename, which validated those RFDs' shapes; this RFD intentionally leaves them to their own proposals. A list subscription is how other Clients learn that a session was archived or renamed.

### Why not compute cost for every session?

Agents differ: Claude Code persists a cumulative `cost-state` per session, Codex only exposes token counts for loaded threads. Requiring a value would force Agents to re-read whole transcripts and maintain price tables. `cost` is sent only when the Agent already has it.

### What alternative approaches did you consider, and why did you settle on this one?

- **Keep it in `_meta`.** That is how it is implemented today, but every Client and Agent pair would need its own extension for a need every history view has.
- **Separate batch methods for state and usage.** Rejected: the list already returns the rows the Client displays, and open sessions have their own `session/update` stream.
- **A total count.** Rejected: expensive for file-based agents and not needed to render the first page.
