Author(s): ACP Remote working draft

## Elevator pitch

> What are you proposing to change?

ACP Remote should cover the useful functionality of Microsoft's Agent Host
Protocol (AHP) natively, without requiring an ACP application to implement AHP
as a second overlapping protocol.

This RFD is the exhaustive parity ledger. It pins the comparison to AHP
`main` commit
[`b4016c0e02dd61393de268fa5e5f1a554d0ca611`](https://github.com/microsoft/agent-host-protocol/tree/b4016c0e02dd61393de268fa5e5f1a554d0ca611),
maps every canonical method, notification, channel, state/action family,
capability, version rule, and error family to an ACP target, and records AHP
ambiguities that ACP should resolve rather than copy.

Parity means that an application can implement the same user-visible host,
session, conversation, workspace, tool, collaboration, customization,
automation, and observability behavior using ACP concepts. It does not require
wire compatibility with AHP or adoption of AHP's shared-reducer architecture.

## Status quo

> How do things work today and what problems does this cause? Why would we change things?

ACP already overlaps AHP in important areas: initialization, sessions,
messages and thoughts, tools and permissions, elicitation, configuration,
MCP, filesystem calls, terminal output, diffs, replay proposals, and remote
transport proposals. AHP adds a broad Host-facing synchronized-state layer,
including resource subscriptions, multiple Clients, multiple chats, resource
watches, interactive terminals, changeset review, annotations, customizations,
telemetry, and automations.

Without an explicit ledger, ACP could add remote transport while still leaving
applications dependent on AHP for the control plane. Conversely, copying all
AHP actions would duplicate mature ACP concepts and inherit correctness and
security gaps.

### Audit baseline

The authoritative inputs are:

- the pinned [AHP source tree](https://github.com/microsoft/agent-host-protocol/tree/b4016c0e02dd61393de268fa5e5f1a554d0ca611);

- the canonical [action registry](https://github.com/microsoft/agent-host-protocol/blob/b4016c0e02dd61393de268fa5e5f1a554d0ca611/types/common/actions.ts);
- the [protocol overview](https://microsoft.github.io/agent-host-protocol/specification/overview.html),
  [transport](https://microsoft.github.io/agent-host-protocol/specification/transport.html),
  [lifecycle](https://microsoft.github.io/agent-host-protocol/specification/lifecycle.html),
  [subscriptions](https://microsoft.github.io/agent-host-protocol/specification/subscriptions.html),
  [authentication](https://microsoft.github.io/agent-host-protocol/specification/authentication.html),
  and [versioning](https://microsoft.github.io/agent-host-protocol/specification/versioning.html);
- every channel specification linked in the channel matrix below; and
- the official [state](https://microsoft.github.io/agent-host-protocol/guide/state-model.html),
  [action](https://microsoft.github.io/agent-host-protocol/guide/actions.html),
  and [reconciliation](https://microsoft.github.io/agent-host-protocol/guide/reconciliation.html)
  guides.

The latest published AHP release at the time of this audit is v0.8.0, while the
pinned source declares protocol 1.0.0 and its
[changelog](https://github.com/microsoft/agent-host-protocol/blob/b4016c0e02dd61393de268fa5e5f1a554d0ca611/CHANGELOG.md)
still labels 1.0.0 unreleased. Automations, automation runs, durable error
response parts, and turn resume are therefore included for `main` parity but
must be treated as an unstable external target.

### Status legend

| Status       | Meaning                                                                             |
| ------------ | ----------------------------------------------------------------------------------- |
| **Existing** | Current ACP v1 or v2 has a substantially equivalent native concept.                 |
| **Partial**  | ACP has an overlapping concept but lacks material AHP semantics.                    |
| **Missing**  | The audited ACP baseline has no native equivalent.                                  |
| **Proposed** | The ACP target is specified by the Host Services RFD or a companion ACP Remote RFD. |

A cell such as **Partial → Proposed** records both the current baseline and the
planned parity disposition. “Existing” never means wire-identical.

## What we propose to do about it

> What are you proposing to improve the situation?

Adopt the ACP-native Host Services model in
[ACP Remote Host Services](./host-services.mdx), together with the remote
transport, authentication/authorization, reliable delivery, and Rust SDK
work. The matrices below are normative scope requirements for claiming AHP
functional parity.

ACP has one remote profile, `acp.remote.v2`. Its dependency graph has
`capabilities.remote.core` as the required root; both
`capabilities.remote.sharedSessions` and `capabilities.remote.hostServices`
depend on `core` and are otherwise independent. These are negotiated capability
sets, not separate wire profiles. Individual Host services remain
subcapabilities of `hostServices`. Full AHP parity requires both optional sets
and every Host subcapability in this ledger.

The full-parity Host set is exactly
`capabilities.remote.hostServices.catalogs`,
`capabilities.remote.hostServices.resources`,
`capabilities.remote.hostServices.workspaces`,
`capabilities.remote.hostServices.terminals`,
`capabilities.remote.hostServices.artifacts`,
`capabilities.remote.hostServices.customizations`,
`capabilities.remote.hostServices.mcp`,
`capabilities.remote.hostServices.automations`, and
`capabilities.remote.hostServices.telemetry`. Omission or `null` of one of
these v2 support markers means that group is unsupported. Core owns
connection delivery and recovery SnapshotSets; `sharedSessions` owns
Session-event subscriptions and multi-chat collaboration through
`capabilities.remote.sharedSessions.multiChat`,
`capabilities.remote.sharedSessions.multiChat.fork`, and
`capabilities.remote.sharedSessions.multiChat.sideChat`; the generic
`resource/*` discovery and subscription surface belongs to the `resources`
Host group. Omission or `null` of a multi-chat support marker means unsupported;
full AHP parity requires all three.

## MCP side-channel method matrix

AHP's `mcp://` channel carries upstream MCP JSON-RPC verbatim after the MCP
server has already initialized. The served union is capability-controlled.
The pinned [AHP MCP channel
specification](https://github.com/microsoft/agent-host-protocol/blob/b4016c0e02dd61393de268fa5e5f1a554d0ca611/docs/specification/mcp-channel.md)
defines this current surface:

| AHP MCP capability | Methods/notifications                                                                                            | ACP status             | ACP native target                                                                          |
| ------------------ | ---------------------------------------------------------------------------------------------------------------- | ---------------------- | ------------------------------------------------------------------------------------------ |
| `serverTools`      | `tools/list`, `tools/call`, optional `notifications/tools/list_changed`.                                         | **Partial → Proposed** | MCP-over-ACP routed connection plus Host tool projection; advertise exact allowed surface. |
| `serverResources`  | `resources/list`, `resources/templates/list`, `resources/read`, optional `notifications/resources/list_changed`. | **Partial → Proposed** | MCP-over-ACP plus ACP resource references; do not duplicate MCP payload schemas.           |
| `logging`          | `logging/setLevel` and `notifications/message` as listed by AHP.                                                 | **Partial → Proposed** | Forward according to upstream MCP direction; expose Host telemetry separately.             |
| `sampling`         | `sampling/createMessage`.                                                                                        | **Partial → Proposed** | Capability-gated MCP-over-ACP reverse request.                                             |

ACP must also match AHP's negative rules: no second MCP
`initialize`/`initialized`, only advertised methods are served, unknown methods
return `-32601`, and channel availability follows MCP customization runtime
state. The MCP App `ui/*` iframe protocol stays outside both ACP and AHP.

## Detailed host-feature parity

### Sessions and summaries

ACP must cover AHP's provider/title/status/activity/origin/project/workspace,
annotation-count, timestamp, change-statistic, read/archive, and `_meta` summary
fields; asynchronous `creating`, `ready`, and `failed` states; MRU-capable
cursor pagination; live additions/removals/updates; default chat; and summary
aggregation across chats. Principal-private read state must not be collapsed
into AHP's globally shared flag.

### Chats, forks, side chats, workers, and transcript references

ACP must cover initial messages, default chat, interactivity, visible-history
fork through a stable completed turn, context-only side chat, selected-text
context, tool-spawned worker chat, ancestry, per-chat workspace subset,
cross-session bounded transcript attachment, one active turn, turn resume, and
history truncation. Every conversational turn is an activity subtype/projection
keyed by the canonical `activityId`, not a second wire identity. ACP should
reject ancestry cycles rather than merely asking Clients to tolerate them.

### Tool lifecycle and input-needed projection

ACP must cover AHP's server/Client/MCP registry; definitions and input/output
schema; partial/final input; edit preview; editable parameters; confirmation
groups/options; user/setting/not-needed decision provenance; risk-judge
loading/result/reason/safety; partial content; authentication-required state;
result confirmation; final structured/unstructured result/error; and text,
embedded resource, content reference, file edit, terminal, and subagent
results. Session aggregate input-needed variants must include chat input, tool
confirmation, Client execution, and authentication.

### Elicitation

ACP's elicitation work must cover text, number, integer, boolean, single-select,
multi-select, constraints/defaults/options/freeform, draft/submitted/skipped
answers, accept/decline/cancel, URL review, and durable association with the
requesting turn/tool. Multi-Client answer arbitration and privacy must be
specified.

### Resources and watches

Parity includes symmetric reads/writes, UTF-8/base64, create-only and ETag,
truncate/append/range semantics, list/copy/delete/move/resolve/mkdir,
permission requests, Client virtual resources, recursive include/exclude
watches, added/updated/deleted batches, and revocation. ACP additionally
requires pagination, bounded/ranged transfer, integrity, URI normalization,
sandbox/symlink rules, watch overflow, and reconnect behavior.

### Terminals

Parity includes catalog, create/dispose, claim by Client/session/chat/turn/tool,
running/exited, raw and command-classified output, input, resize, title, clear,
cwd, exit, command detection/executed/finished, and tool-result preview. ACP
adds claim leases/fencing, bounded scrollback, replay classification, and
uncertain side-effect outcomes.

### Changesets and annotations

Parity includes static/turn/original/modified content references,
computing/ready/error, files, edit/review state, full/file/range review,
server-declared operations, confirmation, icons/groups/status/errors,
follow-up content/external navigation, annotation file/range provenance,
resolved status, and text/Markdown entries. ACP adds per-principal review,
annotation author/timestamps, and trusted icon/navigation policy.

### Customizations and MCP

Parity includes plugin/directory containers; Agents, skills, prompts, rules,
hooks, and MCP leaf nodes; loading/error state; global/workspace/session
enablement; Client-published plugin nonce and child enablement; writable
directory and invocation restrictions; MCP start/stop/live auth states; MCP
Apps capability; and the constrained MCP method union.

### Automations and runs

Parity with unreleased AHP 1.0 includes durable create/update/set/remove;
initial message and session template; enabled state; portable five-field cron;
IANA time zone; Unix day-field OR semantics; daylight-saving and misfire
behavior; minimum interval; discoverable custom event triggers; idempotent
manual runs; pending/running/completed/failed/cancelled lifecycle; trigger
provenance; linked/primary sessions; cancellation; bounded/paginated history;
and one run per occurrence.

### Observability

Parity includes OTLP/JSON logs, traces, metrics, severity-filter templates,
progress tokens, and standard session/turn/tool-call correlation. ACP adds
authority, principal where permitted, chat, request, operation, terminal,
automation, and run correlation plus audit events.

## Shiny future

> How will things will play out once this feature exists?

An ACP Client can connect to a local Agent, a remote Agent, or a multi-agent
Host using one protocol and one typed application model. A Host can offer every
feature currently exposed by AHP: live catalogs, collaborative sessions,
multi-chat history, tools and structured input, remote resources and
terminals, review artifacts, MCP Apps, automations, and telemetry.

ACP's result will be stronger at remote boundaries: authenticated principals
are distinct from Client instances, mutations are idempotent, event loss is
detectable, replay has an atomic boundary, authorization is explicit, and
private state is not accidentally broadcast. An AHP-to-ACP gateway remains
possible, but applications do not need AHP to obtain AHP-class functionality.

## Implementation details and plan

> Tell me more about your implementation. What is your detailed implementation plan?

### Parity gates

ACP may claim parity in stages:

1. **Remote-core parity:** the `acp.remote.v2` profile with
   `capabilities.remote.core`: transport, endpoint authentication,
   authority/client identity, ordered connection delivery, recovery
   SnapshotSets, replay, reliable mutation, common progress/errors, and the
   Rust reconnection base. Generic `resource/*` subscriptions are not Core.
2. **Conversation parity:** `capabilities.remote.sharedSessions`, depending on
   `core`, plus authenticated attachments, Session-event subscriptions,
   attached-Session projections, multi-chat, turn projections keyed by
   `activityId`, message parts/attachments, tools, durable claimed/CAS
   elicitation, steering, queue, drafts, and aggregate input-needed. It does
   not own authority or Session catalogs. Full conversation parity requires
   the exact `sharedSessions.multiChat`, `sharedSessions.multiChat.fork`, and
   `sharedSessions.multiChat.sideChat` markers.
3. **Host-foundation and workspace parity:**
   `capabilities.remote.hostServices`, depending on `core`, plus the exact
   `catalogs`, `resources`, `workspaces`, `terminals`, and `artifacts` markers.
   This gate owns authority/Agent/model/Session catalogs, dynamic
   configuration, generic resource discovery/subscription, content
   references, symmetric operations, watches, interactive terminals,
   changesets, review operations, and annotations.
4. **Extensibility parity:** the exact Host `customizations` and `mcp` markers,
   including MCP lifecycle and constrained side channel; MCP Apps also require
   the matching Client rendering capability. Generic capability negotiation
   remains Core.
5. **Operational parity:** the exact Host `automations` and `telemetry`
   markers. Automations/runs and OTLP streams belong here; common progress,
   audit correlation, and the cross-cutting error registry remain Core.

Full parity requires all five gates: `core`, `sharedSessions`, the three exact
multi-chat support markers, `hostServices`, and all nine exact Host support
markers. A Host can advertise any internally complete subset of the nine Host
markers because `sharedSessions` and `hostServices` are independent children
of Core, but it cannot claim the full Host label or full AHP parity for that
subset.

Each gate requires:

- generated JSON Schema and Rust types;
- normative state/event application rules;
- multi-Client authorization tests;
- transport fault-injection at every request/event disconnect boundary;
- duplicate, stale revision, replay gap, snapshot race, and slow-consumer tests;
- conformance fixtures for unknown versions, variants, capabilities, and
  errors; and
- an AHP gateway mapping test for every matrix row in that gate.

The repository's `scripts/check_remote_ahp_coverage.py` is a narrower CI
sentinel. It verifies 169 pinned, category- and direction-specific surface
entries in mapping rows with an explicit status and nonempty ACP target, plus
the capability, version, and error table sizes. It prevents accidental ledger
omissions; it does not by itself prove behavioral parity. A gate is complete
only when its schema, state rules, conformance traces, and gateway tests above
also pass.

### Rust Client requirements

The Rust SDK parity target includes:

- pluggable stdio, HTTP streaming, and WebSocket transports;
- a connection supervisor with backoff, keepalive, authenticated resume,
  version renegotiation, and server-epoch handling;
- persisted authority/client identity, acknowledged cursors, subscription set,
  and in-flight `operationId` values;
- a revisioned resource store with typed projections for every service;
- optimistic typed operations with conflict/retry and operation-status lookup;
- loss detection and automatic replay or resnapshot before state is reported
  current;
- bounded application event APIs that report lag instead of silently dropping
  state transitions;
- reverse resource, tool, elicitation, and MCP handlers;
- a multi-authority registry keyed by authority identity plus absolute URI; and
- deterministic tests for two Clients concurrently steering, cancelling,
  confirming, answering, editing, claiming a terminal, and losing an owner
  connection.

## Frequently asked questions

> What questions have arisen over the course of authoring this document or during subsequent discussions?

### Does parity require ACP to use AHP method or action names?

No. It requires native functional coverage. ACP should retain its session,
prompt, update, tool, permission, elicitation, MCP, and content concepts and
introduce specialized services where their semantics matter.

### Why is `dispatchAction` marked Missing rather than Proposed?

The AHP behavior is covered, but the mechanism is intentionally not adopted.
A generic unacknowledged notification cannot safely express remote side
effects. ACP uses typed idempotent operations and typed resource events.

### Is unreleased AHP 1.0 automation support required?

It is required for parity with the pinned `main` commit and optional for parity
with published AHP v0.8.0. ACP should ship it as an independently negotiated,
experimental capability until both designs stabilize.

### Does this make an AHP bridge impossible?

No. The explicit ledger makes a bridge easier: AHP snapshots/actions map to ACP
resource snapshots/events, while AHP commands map to typed ACP operations. A
bridge must synthesize the stronger ACP identity, idempotency, authorization,
and replay guarantees or advertise that it cannot provide them.
