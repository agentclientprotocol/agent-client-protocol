---
title: "Agent Plan"
description: "How Agents communicate their execution plans"
---

A plan describes how the Agent intends to carry out a task. It can be a list of steps or a Markdown document.

Agents **MAY** send plans to Clients through [`session/update`](/protocol/v2/prompt-lifecycle#3-agent-reports-output) notifications and update them as work progresses.

`plan_update` carries a `plan` object with a `type` discriminator and a required `planId` so Clients can track multiple plans independently.

Agents can send `items` or `markdown` plans and remove them with `plan_removed`. No Client capability is required. Clients **MUST** accept both plan types and `plan_removed`. Accepting a plan does not require displaying it.

## Creating plans

When the language model creates an execution plan, the Agent **SHOULD** report it to the Client with `plan_update`.

### Item-based plans

```json
{
  "jsonrpc": "2.0",
  "method": "session/update",
  "params": {
    "sessionId": "sess_abc123def456",
    "update": {
      "sessionUpdate": "plan_update",
      "plan": {
        "type": "items",
        "planId": "plan-1",
        "entries": [
          {
            "content": "Analyze the existing codebase structure",
            "priority": "high",
            "status": "pending"
          },
          {
            "content": "Identify components that need refactoring",
            "priority": "high",
            "status": "pending"
          },
          {
            "content": "Create unit tests for critical functions",
            "priority": "medium",
            "status": "pending"
          }
        ]
      }
    }
  }
}
```

<ParamField path="plan.type" type="string" required>
  The plan content type.
</ParamField>

<ParamField path="plan.planId" type="PlanId" required>
  A unique identifier for this plan within the session.
</ParamField>

<ParamField path="plan.entries" type="PlanEntry[]" required>
  An array of [plan entries](#plan-entries) representing the tasks to be
  accomplished.
</ParamField>

### Markdown plans

```json
{
  "jsonrpc": "2.0",
  "method": "session/update",
  "params": {
    "sessionId": "sess_abc123def456",
    "update": {
      "sessionUpdate": "plan_update",
      "plan": {
        "type": "markdown",
        "planId": "implementation-plan",
        "content": "## Steps\n- [ ] Refactor module\n- [ ] Add tests",
        "path": "/home/user/project/PLAN.md"
      }
    }
  }
}
```

<ParamField path="plan.content" type="string" required>
  The complete plan as [Markdown](/protocol/v2/content#plain-text-and-markdown),
  not just the text that changed.
</ParamField>

<ParamField path="plan.path" type="string | null">
  The absolute path of the file that holds this plan. Omission and `null` are
  equivalent and mean the plan has no file.
</ParamField>

`path` **MUST** be an absolute path. A Client that displays the plan uses `content` whether or not it can reach the file. It can use `path` to open the file.

## Removing plans

Agents can remove a plan by sending `plan_removed` with the plan ID:

```json
{
  "jsonrpc": "2.0",
  "method": "session/update",
  "params": {
    "sessionId": "sess_abc123def456",
    "update": {
      "sessionUpdate": "plan_removed",
      "planId": "plan-1"
    }
  }
}
```

Agents **SHOULD** send `plan_removed` when a plan is cancelled, for example when the user rejects it or the Agent abandons it. A finished plan doesn't need to be removed. Clients **MUST** ignore `plan_removed` for a `planId` they don't know.

To clear the plan for older Clients that don't recognize `plan_removed`, Agents can first send an `items` update with the same `planId` and `entries: []`.

## Extensibility

`plan.type` values can be custom or future variants when Clients can preserve or display them generically. Custom plan content types **MUST** begin with `_`. Unknown non-underscore plan content types are reserved for future ACP variants.

Every plan content variant, including custom or future variants, **MUST** carry a `planId`.

## Plan entries

Each plan entry represents a specific task or goal within the overall execution strategy:

<ParamField path="content" type="string" required>
  A human-readable description of what this task aims to accomplish. It can be
  plain text or [Markdown](/protocol/v2/content#plain-text-and-markdown), like a
  text content block.
</ParamField>

<ParamField path="priority" type="PlanEntryPriority" required>
  The relative importance of this task.

- `high`
- `medium`
- `low`

Custom or future priority values can be used for display hints. Custom priorities **MUST** begin with `_`. Unknown non-underscore priorities are reserved for future ACP variants.

</ParamField>

<ParamField path="status" type="PlanEntryStatus" required>
  The current execution status of this task

- `pending`
- `in_progress`
- `completed`
- `cancelled`

Custom or future status values can be used when Clients can preserve or display a generic plan-entry state. Custom statuses **MUST** begin with `_`. Unknown non-underscore statuses are reserved for future ACP variants.

</ParamField>

## Updating plans

As the Agent progresses through the plan, it **SHOULD** report updates by sending more `session/update` notifications with the same `sessionUpdate: "plan_update"` structure and `planId`.

Each `plan_update` replaces the whole plan with that `planId`, whatever its `type`, including when the type differs from the previous update. A Client that doesn't understand the new `type` still treats the update as replacing that plan, so it stops showing the previous content.

For item-based plans, the Agent **MUST** send a complete list of all plan entries in each update and their current status. The Client **MUST** replace the current contents of that plan completely. An empty `entries` array empties the plan. Clients **MAY** hide an empty plan.

### Dynamic planning

Plans can change during execution. The Agent **MAY** add, remove, or modify plan entries as it discovers new requirements or completes tasks.
