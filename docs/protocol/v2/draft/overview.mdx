The Agent Client Protocol allows [Agents](#agent) and [Clients](#client) to communicate by exposing methods that each side can call and sending notifications to inform each other of events.

## Communication Model

The protocol follows the [JSON-RPC 2.0](https://www.jsonrpc.org/specification) specification with two types of messages:

- Methods are request-response pairs that expect a result or error.
- Notifications are one-way messages that don't expect a response.

Unlike base JSON-RPC, request IDs **MUST** be a string or an integer, never
`null`. An error response has `id: null` only when the request ID could not be
determined.
A receiver rejects a message that has a `method` and an `id` of `null` with `-32600` (Invalid request) and `id: null`. It does not treat the message as a notification.

Both sides send requests, and each side chooses IDs for its own requests independently, so the same ID can be in use in both directions. A sender **MUST NOT** reuse an ID while a request with that ID is still awaiting a response.

Unlike base JSON-RPC, ACP does not use batches. See [Transports](/protocol/v2/draft/transports#no-batches).

## Message flow

A typical flow follows this pattern:

<Steps>
<Step title="Initialization Phase">

- Client → Agent: `initialize` to establish connection
- Client: completes an advertised authentication flow if required. For example,
  `auth/login` for an Agent-handled method or launch and reconnect for a
  terminal method

</Step>

<Step title="Session Setup - either:">

- Client → Agent: `session/new` to create a new session
- Client → Agent: `session/resume` to resume an existing session

</Step>

<Step title="Prompt Lifecycle">
   - Client → Agent: `session/prompt` to send user message
   - Agent → Client: `session/prompt` response once the prompt is accepted
   - Agent → Client: `session/update` notifications for accepted messages, state updates, progress updates, and user-facing notices
   - Agent → Client: Permission requests as needed
   - Client → Agent: `session/cancel` to cancel foreground work if needed
   - Agent → Client: An idle `state_update` with a stop reason when foreground work ends, even if background activity continues
</Step>
</Steps>

## Agent

Agents are programs that use generative AI to autonomously modify code. They typically run as subprocesses of the Client.

### Baseline methods

Some baseline methods are optional as a group. An Agent that returns a non-empty `authMethods` list **MUST** implement both `auth/login` and `auth/logout`. If `authMethods` is omitted or empty, Clients **MUST NOT** call either method. The `session/*` methods require `capabilities.session`.

## Request cancellation

Either side can send [`$/cancel_request`](/protocol/v2/draft/cancellation) to cancel a request it sent (no response expected).

## Retrying requests

When a response is lost, for example because the connection ended, the sender cannot tell whether the request took effect. Each method has one of four retry classes:

| Class       | Meaning                                                                                                                          | Retry rule                                                                                              |
| ----------- | -------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| Idempotent  | Sending the request again with the same parameters has no effect beyond the first. This includes read-only requests.             | The sender may send it again as is. The response reports current state.                                 |
| Keyed       | Each request performs the operation again, and a duplicate does real damage. The request accepts an `idempotencyKey`.            | The Client may send it again with the same `idempotencyKey`. Without a key, a retry is a new operation. |
| Duplicating | Each request creates something new, and an extra one does little harm.                                                           | The Client may send it again. If the first request also took effect, what it created is left unused.    |
| Not retried | Notifications, which have no response to lose, and messages that only have meaning on one connection or for one pending request. | The sender doesn't send it again. It recovers through `session/resume` or a new connection.             |

Requests the Client sends:

| Method                                                               | Class                  | Sending it again with the same parameters                                                                                                                                                                            |
| -------------------------------------------------------------------- | ---------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `initialize`                                                         | Not retried            | The Client can repeat it before its first other request, and the latest successful one applies. It is not sent again after that. See [Version negotiation](/protocol/v2/draft/initialization#version-negotiation).   |
| `auth/login`                                                         | Idempotent             | Leads to the same authenticated state. The Agent may show the user a second login flow.                                                                                                                              |
| `auth/logout`                                                        | Idempotent             | Succeeds when the authenticated state has already ended.                                                                                                                                                             |
| `session/new`                                                        | Duplicating            | Creates a second session. If the first response was lost, the Client never learned that session's ID. The Agent [may discard](/protocol/v2/draft/session-setup#session-lifecycle) a session that was never prompted. |
| `session/resume`                                                     | Idempotent             | Synchronizes the session again. The request's MCP servers and workspace roots replace the previous ones, which are the same on a retry.                                                                              |
| `session/prompt`                                                     | Keyed                  | Without a key, inserts a second user message and may start the work twice. See [Retrying a prompt](/protocol/v2/draft/prompt-lifecycle#retrying-a-prompt).                                                           |
| `session/set_config_option`                                          | Idempotent             | Sets the same value and returns the complete current options. A retry sent after a later change to the same option overwrites that change, so Clients retry before sending further changes.                          |
| `session/list`                                                       | Idempotent             | Read-only.                                                                                                                                                                                                           |
| `session/close`                                                      | Idempotent             | Succeeds.                                                                                                                                                                                                            |
| `session/delete`                                                     | Idempotent             | Succeeds. A Client treats `-32002` as a successful delete.                                                                                                                                                           |
| `tool_call/cancel`, `terminal/cancel`                                | Idempotent             | Has no second effect. Once the tool call is final or the terminal has exited, the retry gets `-32602`, and the `tool_call_update` or `terminal_update` reports what happened.                                        |
| `session/fork`                                                       | Duplicating            | **Draft only.** Creates a second copy of the source session. The Client can find the unused copy with `session/list` and remove it with `session/delete`.                                                            |
| `session/archive`, `session/unarchive`                               | Idempotent             | **Draft only.** Succeeds.                                                                                                                                                                                            |
| `session/set_title`, `providers/set`, `providers/disable`            | Idempotent             | **Draft only.** Sets the same value again.                                                                                                                                                                           |
| `session/status`, `session/options`, `providers/list`, `auth/status` | Idempotent             | **Draft only.** Read-only.                                                                                                                                                                                           |
| `mcp/message`                                                        | Defined by MCP         | **Draft only.** Depends on the MCP message it carries.                                                                                                                                                               |
| `proxy/initialize`, `proxy/successor`                                | As the carried message | **Draft only.** `proxy/successor` carries another message. The class of the carried message applies, and its `idempotencyKey` is forwarded unchanged.                                                                |

Requests the Agent sends:

| Method                       | Class          | Sending it again with the same parameters                                                                                                                                                                                                                                     |
| ---------------------------- | -------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `session/request_permission` | Idempotent     | The Client shows the request again. The response is the user's decision, and the action it allows stays with the Agent. After the connection is lost, the Agent [reestablishes or resolves](/protocol/v2/draft/session-setup#current-state-synchronization) pending requests. |
| `elicitation/create`         | Idempotent     | The same as `session/request_permission`. A URL-mode request carries an `elicitationId` that links the completion notification.                                                                                                                                               |
| `mcp/message`                | Defined by MCP | **Draft only.** Depends on the MCP message it carries.                                                                                                                                                                                                                        |

Notifications:

| Method                 | Class       | Sending it again with the same parameters                                                                                                                                                                              |
| ---------------------- | ----------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `session/cancel`       | Not retried | Does nothing on an idle session. A copy that arrives after new work has started cancels that work, so the Client does not send it again later.                                                                         |
| `$/cancel_request`     | Not retried | Receivers ignore a request ID that is unknown or already answered.                                                                                                                                                     |
| `session/update`       | Not retried | Upserts replace state by entity ID, but chunks append, so a resent chunk duplicates content. A Client that missed updates requests replay with [`session/resume`](/protocol/v2/draft/session-setup#resuming-sessions). |
| `elicitation/complete` | Not retried | Reports the same state again.                                                                                                                                                                                          |
| `auth/status_update`   | Not retried | **Draft only.** Reports the same state again.                                                                                                                                                                          |

## Argument requirements

- All file paths in the protocol **MUST** be absolute, in the native syntax of the machine the Agent runs on (for example `/home/user/project`, `C:\Users\user\project`, or `\\server\share\project`), and are not URIs.
- Line numbers are 1-based

## Error handling

All methods follow standard JSON-RPC 2.0 [error handling](https://www.jsonrpc.org/specification#error_object):

- Successful responses include a `result` field
- Errors include an `error` object with `code` and `message`
- Notifications never receive responses (success or error)

See [Errors](/protocol/v2/draft/error) for the error codes ACP uses and when to use them.

## Conventions

Unless explicitly defined otherwise in the schema, ACP-defined JSON object property keys use `camelCase`. String values carried by discriminator fields use `snake_case`. The JSON-RPC envelope fields (`jsonrpc`, `id`, `method`, `params`, `result`, and `error`) follow the JSON-RPC 2.0 specification.

For an optional field whose schema allows `null`, omitting it and setting it to `null` are equivalent, unless the field says otherwise. Optional fields whose schema does not allow `null`, such as most arrays and objects, are omitted rather than sent as `null`. Upsert updates are the exception: there an omitted field leaves the stored value unchanged and `null` clears it.

Selected enum-like fields and tagged unions can define custom or future fallbacks. For those fields, `_`-prefixed values are reserved for implementation-specific extensions, while unknown non-underscore values are reserved for future ACP variants.

## Extensibility

Implementations can extend the protocol without breaking compatibility:

- Add custom data using `_meta` fields
- Create custom methods by prefixing their name with underscore (`_`)
- Advertise custom capabilities during initialization

See [Extensibility](/protocol/v2/draft/extensibility) for details.
