---
title: "Slash Commands"
description: "Advertise available slash commands to clients"
---

Agents can advertise a set of slash commands that users can invoke. These commands provide quick access to specific agent capabilities and workflows. Commands are run as part of regular [prompt](/protocol/v2/draft/prompt-lifecycle) requests where the Client includes the command text in the prompt.

## Advertising commands

### Initial commands

An Agent with commands **MUST** include them in `availableCommands` in the `session/new`, `session/resume`, and, when supported, `session/fork` responses, alongside `configOptions` when supported, since a setup response replaces the Client's command list. This lets the Client display commands as soon as [session setup](/protocol/v2/draft/session-setup#initial-session-state) completes, without requiring an `available_commands_update` notification before the `session/new` response.

For example, a `session/new` response can advertise a command with text input:

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "result": {
    "sessionId": "sess_abc123def456",
    "availableCommands": [
      {
        "type": "command",
        "name": "web",
        "description": "Search the web for information",
        "input": {
          "type": "text",
          "hint": "query to search for"
        }
      }
    ]
  }
}
```

<ResponseField name="availableCommands" type="AvailableCommand[]">
  Optional complete list of commands available in this session. Omission or `[]`
  means none, and Clients replace any list they hold with it. Empty lists are
  omitted when serializing setup responses.
</ResponseField>

`null` is not a valid outbound value for this field.

Agents that advertise `session.options` can also return advisory `availableCommands` from `session/options`, before a session exists. That list is a preview. The setup response replaces it. See [Options before a session exists](/protocol/v2/draft/session-config-options#options-before-a-session-exists-unstable).

### Notifications

After session setup, the Agent **MAY** announce commands that were not included in the response, or update the list, via the `available_commands_update` session notification:

```json
{
  "jsonrpc": "2.0",
  "method": "session/update",
  "params": {
    "sessionId": "sess_abc123def456",
    "update": {
      "sessionUpdate": "available_commands_update",
      "availableCommands": [
        {
          "type": "command",
          "name": "web",
          "description": "Search the web for information",
          "input": {
            "type": "text",
            "hint": "query to search for"
          }
        },
        {
          "type": "command",
          "name": "test",
          "description": "Run tests for the current project"
        },
        {
          "type": "command",
          "name": "plan",
          "description": "Create a detailed implementation plan",
          "input": {
            "type": "text",
            "hint": "description of what to plan"
          }
        }
      ]
    }
  }
}
```

The notification's `availableCommands` array is the complete replacement list, not a delta. An empty array clears all advertised commands.

### AvailableCommand

Each command carries a required `type` discriminator. The stable type is `command`, a slash command the user invokes by including it in a prompt. The unstable `skill` type is described in [Skills](#skills-unstable). The fields below are those of a `command` entry.

<ResponseField name="type" type="string" required>
  The kind of command. `"command"`, or `"skill"` for a
  [skill](#skills-unstable).
</ResponseField>

<ResponseField name="name" type="string" required>
  The command name without the leading `/`, such as `web`, `test`, or `plan`.
  **MUST NOT** contain whitespace and **MUST** be unique within the list.
</ResponseField>

<ResponseField name="description" type="string" required>
  Human-readable description of what the command does
</ResponseField>

<ResponseField name="input" type="AvailableCommandInput">
  Optional input specification for the command
</ResponseField>

Command entries can add custom or future `type` values. Custom command types **MUST** begin with `_`. Unknown non-underscore command types are reserved for future ACP variants. Every command type carries `name` and `description`, and each type defines how its entries are invoked. Clients that don't understand a command type should preserve it when storing, replaying, proxying, or forwarding command metadata, and otherwise ignore it. They **MUST NOT** display it as a slash command. Entries without a `type`, or with a known `type` that doesn't match its schema, are invalid and are skipped like any other invalid command item.

### AvailableCommandInput

Currently supports text input with `type: "text"`:

<ResponseField name="hint" type="string" required>
  A hint to display when the input hasn't been provided yet
</ResponseField>

Command input specifications can add custom or future `type` values. Custom input types **MUST** begin with `_`. Unknown non-underscore input types are reserved for future ACP variants. Clients that cannot render an input specification should preserve it when storing, replaying, proxying, or forwarding command metadata, and otherwise display the command without structured input.

## Dynamic updates

The Agent can update the list of available commands at any time during a session by sending another `available_commands_update` notification. Each notification replaces the list previously advertised in a setup response or notification, including `[]` to clear it. Agents can use this to add commands as context changes, remove commands that no longer apply, or update descriptions.

## Running commands

Commands are included as regular user messages in prompt requests:

```json
{
  "jsonrpc": "2.0",
  "id": 3,
  "method": "session/prompt",
  "params": {
    "sessionId": "sess_abc123def456",
    "prompt": [
      {
        "type": "text",
        "text": "/web agent client protocol"
      }
    ]
  }
}
```

A prompt invokes a `command` entry when its first text block starts with `/` followed by the command `name`. The Agent decides how to interpret the prompt. Clients recognizing a command for highlighting or completion **SHOULD** require the name to be followed by whitespace or the end of the text block, so `/web foo` matches `web`, `/webfoo` does not, and `/web-search foo` matches `web-search`, not `web`. The rest of that text block, after the name and the whitespace following it, is the command's input. Text naming a command the Agent did not advertise is an ordinary prompt. Commands may be accompanied by any other user message content types (images, audio, etc.) in the same prompt array.

The same [prompt insertion contract](/protocol/v2/draft/prompt-lifecycle#2-prompt-accepted) applies to commands: the successful response returns the inserted user message's `messageId`, and the Agent reports that message through a `user_message` update or `user_message_chunk` updates with the same ID.

If a command is handled locally and the runtime does not record it, the adapter inserts a live-only user message into the ACP conversation. It need not wait for a runtime insertion event or keep a permanent transcript entry. If the command is retained and replayed later, it uses the same message ID and is not executed again.

For example, an adapter can report a locally handled `/compact` as a live-only user message containing `/compact`, even if the runtime records only a summary. The ACP user message represents the command invocation. It need not match the runtime's transcript or expanded instructions.

Local handling still uses the
[foreground lifecycle](/protocol/v2/draft/prompt-lifecycle#work-boundaries-and-local-commands).
From idle, the Agent **MUST** report an active state for command handling and
`idle` when no foreground work remains, even if no model call or tool invocation
occurs. A command with no user-action wait uses `running` → `idle`, and
**SHOULD** include `stopReason: "end_turn"` for successful completion.
Completing an individual command while other foreground activity continues
does not require an idle boundary.

## Skills (unstable)

A `skill` entry advertises an [Agent Skill](https://agentskills.io/specification) that the user can invoke. Clients use the type to label skills, list them apart from the Agent's other commands, and open the file that defines a skill. See the [RFD](/rfds/agent-skills).

The Agent **MUST NOT** send `skill` entries unless the Client advertised support by supplying `capabilities.session.commands.skill` in its `initialize` request. Omitting `session`, `commands`, or `skill`, or setting any of them to `null`, means the Client does not advertise support. For those Clients, an Agent can advertise its skills as `command` entries.

An Agent that sends `skill` entries **MUST** advertise the [`session.prompt.skill` capability](/protocol/v2/draft/initialization#session-prompt-capabilities).

Skills are delivered like other commands, in `availableCommands` in setup responses and `available_commands_update` notifications:

```json
{
  "type": "skill",
  "name": "pdf-processing",
  "description": "Extract text and tables from PDF files",
  "path": "/home/alice/.agents/skills/pdf-processing/SKILL.md"
}
```

<ResponseField name="name" type="string" required>
  The name the Client uses to refer to the skill. **MUST NOT** contain
  whitespace and **MUST** be unique within the list, across commands and skills.
  It need not match the `name` in the skill's frontmatter. An Agent with two
  skills of the same name, or a skill and a command of the same name, qualifies
  one of them, for example as `plugin:pdf-processing`.
</ResponseField>

<ResponseField name="description" type="string" required>
  Human-readable description of what the skill does, shown to users. A skill's
  frontmatter description is written for the model and can be long. An Agent
  that has a shorter description meant for users **SHOULD** send that one.
</ResponseField>

<ResponseField name="path" type="string">
  Optional absolute path, on the machine the Agent runs on, of the file that
  defines the skill, normally its `SKILL.md`. Agents omit it for skills with no
  such file, such as skills built into the Agent or served by an MCP server.
  Clients can use it to show where a skill lives or to open it. A Client that
  doesn't share a filesystem with the Agent can't open it.
</ResponseField>

A `skill` entry has no `input` specification. For `path` and `_meta`, omission and `null` are equivalent. A Client treats an invalid value in one of these fields as absent and keeps the entry.

Agents **SHOULD** advertise only skills the user can invoke.

`name`, `description`, and `path` come from the Agent and, through it, from whoever wrote the skill. Clients treat them as untrusted, as they do command names and descriptions, and open `path` only on a user action.

### Invoking a skill

A Client invokes a skill by putting a [`skill` content block](/protocol/v2/draft/content#skill-reference-unstable) in the prompt. The `/name` syntax in [Running commands](#running-commands) applies only to `command` entries.

```json
{
  "jsonrpc": "2.0",
  "id": 3,
  "method": "session/prompt",
  "params": {
    "sessionId": "sess_abc123def456",
    "prompt": [
      { "type": "skill", "name": "pdf-processing" },
      {
        "type": "text",
        "text": "Pull the tables out of report.pdf and summarize them."
      }
    ]
  }
}
```

The Agent's `session.prompt.skill` capability says where the block may appear:

- `skill: {}` means a prompt may contain one `skill` block, and it has to be the first block.
- `skill: { "inline": {} }` means a prompt may contain any number of `skill` blocks, at any position:

  ```json
  [
    { "type": "text", "text": "Pull the tables out of report.pdf with " },
    { "type": "skill", "name": "pdf-processing" },
    { "type": "text", "text": ", then chart them with " },
    { "type": "skill", "name": "charts" },
    { "type": "text", "text": "." }
  ]
  ```

The same rules apply at both levels:

- `name` is the `name` of a `skill` entry in the session's current command list. The block carries no input.
- The Agent **MUST** treat each block as the user explicitly invoking that skill for this prompt, and applies the skill to the prompt as a whole. How it does that is up to the Agent. It can, for example, load the skill's instructions for the turn, or run the skill with the rest of the prompt as its input.
- Clients **MUST NOT** send a `skill` block that the Agent's capability doesn't allow. The Agent **MUST** reject a prompt that contains one, or one whose `name` it can't resolve to a skill the user can invoke, with `-32602` and without inserting it.
- The block is part of the inserted user message, so the Agent reports it in `user_message` and replays it. When replaying to a Client that didn't advertise `session.commands.skill`, the Agent **MAY** replace it with text.
- A `resource_link` or embedded resource that points at a skill's file is ordinary context. It does not invoke the skill.

How the Client lets the user pick a skill, with `$`, `@`, `/`, or a menu, is up to the Client.
