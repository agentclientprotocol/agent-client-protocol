Failed requests return a [JSON-RPC 2.0 error object](https://www.jsonrpc.org/specification#error_object):

- `code`: an integer identifying the kind of error
- `message`: a short human-readable description
- `data` (optional): additional information whose shape depends on the code

```json
{
  "jsonrpc": "2.0",
  "id": 3,
  "error": {
    "code": -32002,
    "message": "Resource not found",
    "data": { "sessionId": "sess_abc123def456" }
  }
}
```

## Error codes

| Code     | Message                      | Meaning                                                                                                                                                         |
| -------- | ---------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `-32700` | Parse error                  | The message is not valid JSON.                                                                                                                                  |
| `-32600` | Invalid request              | The message is not a valid request object, a request other than `initialize` arrived before initialization, or `initialize` was repeated after another request. |
| `-32601` | Method not found             | The receiver does not implement the method.                                                                                                                     |
| `-32602` | Invalid params               | The parameters are malformed or contain a value the receiver does not support.                                                                                  |
| `-32603` | Internal error               | The receiver failed unexpectedly.                                                                                                                               |
| `-32800` | Request cancelled            | The request was [cancelled](/protocol/v2/draft/cancellation).                                                                                                   |
| `-32000` | Authentication required      | The request requires [authentication](/protocol/v2/draft/authentication) first, or an `auth/login` attempt failed.                                              |
| `-32002` | Resource not found           | A referenced resource, such as a session, does not exist.                                                                                                       |
| `-32022` | Unsupported protocol version | The Agent supports no [protocol version](/protocol/v2/draft/initialization#version-negotiation) at or below the requested one.                                  |

Receivers **MUST** treat an unrecognized code as a generic failure. Implementation-specific errors **SHOULD** use codes outside `-32768` to `-32000` and `-32899` to `-32800`, which are reserved for JSON-RPC and ACP. ACP takes `-32800` (Request cancelled) from the second range, which LSP also reserves.

## Common cases

### Unknown methods

A receiver that does not implement a method, or receives a capability-gated method it did not advertise, **MUST** respond with `-32601`. This applies to custom and standard methods alike. Notifications can't be answered, so receivers **SHOULD** ignore unknown ones.

### Invalid parameters

Malformed parameters and unsupported values get `-32602`. For example, an invalid `session/list` cursor, or in `session/set_config_option` an unknown `configId`, an invalid value, or a value `type` that is unsupported or doesn't match the option.

### Unknown sessions

If a session-scoped request names a session that does not exist or is not active on the connection, the Agent **MUST** respond with `-32002` and set `data.sessionId` to the requested ID. A session is active once it is created, resumed, or forked on the connection, until it is closed or the connection ends. See [Session Lifecycle](/protocol/v2/draft/session-setup#session-lifecycle).

This applies to `session/prompt` and `session/set_config_option`, and to `session/resume` of a session that does not exist or was deleted. `session/close` and `session/delete` are exceptions: Agents **SHOULD** still return success when closing a session that does not exist or is not active, or deleting one that does not exist. Clients **SHOULD** treat a `-32002` response to either as success. See [Closing Active Sessions](/protocol/v2/draft/session-setup#closing-active-sessions) and [Deleting Sessions](/protocol/v2/draft/session-delete).

### Requests before initialization

Agents **MUST** reject any request other than `initialize` that arrives before initialization completes with `-32600`, and ignore notifications. They also reject an `initialize` repeated after another request with `-32600`. See [Before Initialization Completes](/protocol/v2/draft/initialization#before-initialization-completes).

## Unstable features

- `session/fork` of a session that does not exist gets `-32002`, as for [unknown sessions](#unknown-sessions). The source session only has to exist. It doesn't have to be active on the connection.
- `session/set_title` of a session that does not exist gets `-32002`. The session only has to exist. It doesn't have to be active on the connection. A title the Agent rejects gets `-32602`.
- A `systemPrompt` the Agent cannot apply gets an error, `-32602` recommended. See [System Prompt](/protocol/v2/draft/session-setup#system-prompt-unstable).
- `providers/*` methods called without the [`providers` capability](/protocol/v2/draft/initialization#agent-capabilities) get `-32601`.
